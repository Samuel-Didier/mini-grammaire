# AGENTS.md

« Ma Mini-Grammaire » — appli web d'apprentissage du français. PHP 8.2 + Fat-Free Framework 3.9 (F3) en MVC, MariaDB, JS/CSS vanilla, **aucun build ni gestionnaire front** (pas de npm/bundler : `<link>`/`<script>` sont écrits dans les pages). `DOCUMENTATION.md` décrit les fonctionnalités, mais son tableau de routes est faux (prefixe `/mini-grammaire` inexistant).

## Exécution — DDEV obligatoire (pas de PHP sur l'hôte)

- `ddev start` → https://mini-grammaire.ddev.site (nginx-fpm, MariaDB 11.8, docroot = racine du projet). `ddev describe` liste les URL (phpMyAdmin sur `:8036`).
- Tout PHP/Composer/SQL passe par le conteneur : `ddev exec composer install`, `ddev exec php -l <fichier>`, `ddev mysql`.
- Vérification d'un changement : `ddev exec php -l` sur chaque fichier touché, puis `curl -sk -o /dev/null -w '%{http_code}' https://mini-grammaire.ddev.site<route>` sur **chaque route modifiée** (302 vers `/login` = session absente, c'est normal). Aucun test, lint ni CI n'existe.

## Base de données

- Import : `ddev mysql db < mini_gram.sql` (users, astuces, favoris, progression) **et** `ddev mysql db < mini_grammaire_codes.sql` (table `mini_grammaire_codes`, 158 fiches `code`/`category`/`description`/`detail`/`example` — absente de `mini_gram.sql`, donc les pages mini-grammaire plantent si on l'oublie ; `detail`/`example` sont nullables et plusieurs fiches partagent un même code, ex. `G1.1` en 4 occurrences). `first.sql` ne fait que `create database mini_gram;`.
- `migrations/*.sql` = instructions ALTER **appliquées à la main** (aucun outil de migration). Pièges : `2026_08_23_add_consecutive_days.sql` et `2026_08_23_add_streak_freeze.sql` ajoutent **tous deux** `last_activity_date` → ne pas les appliquer en l'état ; `2026_09_23_add_perf_indexes.sql` impose de vérifier les doublons avant d'ajouter les `UNIQUE`.
- `users.deleted_at` (DATETIME NULL) = suppression logique des comptes, ajoutée par `migrations/2026_09_28_add_user_soft_delete.sql`. Tant qu'elle n'est pas appliquée, `User::softDeleteSupported()` renvoie `false`, la connexion fonctionne, mais les boutons de désactivation sont masqués et `softDelete/restore` renvoient une erreur.
- Connexion persistante (« Se souvenir de moi ») : `migrations/2026_09_29_add_remember_me.sql` ajoute `users.remember_token` (SHA-256 du jeton, jamais le jeton en clair) et `users.remember_expires`. Tant qu'elles ne sont pas appliquées, `User::rememberSupported()` renvoie `false`, la case à cocher est masquée et aucun cookie n'est posé — l'application fonctionne normalement. Le cookie s'appelle `mg_souvenir` (`BaseController::SOUVENIR_COOKIE`), dure `User::REMEMBER_JOURS` (7) jours et est posé/retiré via l'API F3 `$f3->set('COOKIE.…', …)` / `$f3->clear('COOKIE.…')` (héritage automatique de `path`/`secure`/`httponly`/`samesite`). `BaseController::beforeroute` restaure la session **avant** la résolution du rôle, donc `userRole`, `canDashboard` et le journal des requêtes sont corrects dès cette requête. Le jeton est révoqué à la déconnexion, à tout changement de mot de passe (`updateProfile`, `updateByAdmin`, `resetPassword`) et à la désactivation d'un compte. `session_regenerate_id(true)` est désormais appelé à la connexion **et** à la reconnexion silencieuse.
- Avatars : `users.image` ne stocke que l'**identifiant** d'un avatar du catalogue (ex. `chat.svg`), jamais un chemin ni une URL. Le catalogue est le tableau `User::catalog()` (`identifiant => émoji`) ; `User::avatars()` renvoie la liste triée, `User::avatarEmoji()` l'émoji d'un identifiant, `User::normalizeAvatar()` la liste blanche, `''` retire l'avatar, `User::setAvatar()` est le seul point d'écriture. ⚠️ l'émoji est rendu en **texte HTML** (`<span class="avatar-emoji">`), pas dans un fichier SVG chargé par `<img>` : un SVG en contexte image n'a pas accès à la police émoji du système, et le glyphe s'affiche alors en monochrome ou vide sur les navigateurs de bureau. Ajouter un avatar = une ligne dans `User::catalog()`. La page `/profile` affiche l'émoji (ou les initiales si `image` est vide) et un bouton ✏️ ouvre une popup ; le choix part en AJAX vers `POST /profile/avatar` (en-tête `X-CSRF-Token` obligatoire, sinon 403 — la réponse renvoie `emoji` pour le re-rendu) ; `Auth::avatarsForView()` alimente la grille des deux pages. ⚠️ `profile_edit.html` ne charge que `auth.css` : la grille `.avatar-picker`/`.avatar-option` vit dans `profile.css`, qui doit aussi y être lié.
- La BD DDEV locale n'a pas les colonnes de streak ; `ConsecutiveDays::recordActivity` les détecte et renvoie 1 au lieu de planter. Le modèle `Streak` n'est appelé nulle part.
- Tables du quiz, créées par `migrations/2026_09_29_add_quiz_tables.sql` puis remplies par `migrations/2026_09_29_seed_quiz_questions.sql` (**dans cet ordre**, le seed n'est pas idempotent) : `quiz_questions` (`categorie` = slug, `libelle_categorie`, `niveau`, `difficulte`, `question`, `explication`) et `quiz_propositions` (`question_id`, `libelle`, `ordre`, `est_correcte`). Un quiz = couple `(categorie, niveau)` ; `niveau = 'tous'` = test de niveau. 20 questions / 80 propositions en base.
- Journal des requêtes : `migrations/2026_09_29_add_request_logs.sql` crée `request_logs` (`user_id`/`username`/`role` figés, `methode`, `chemin`, `uri`, `statut`, `duree_ms`, `ip`, `user_agent`, `referer`, `cree_le`). ⚠️ `user_id` n'a **aucune** clé étrangère : les lignes survivent à la suppression d'un compte et le nom affiché est un instantané. Tant que la table est absente, l'application fonctionne normalement (journal ignoré, `/dashboard/logs` affiche un avertissement) — c'est volontairement tolérant pour ne pas casser la prod avant l'application de la migration.
- ⚠️ `2026_09_23_add_perf_indexes.sql` pose un `UNIQUE` sur `progression (user_id, niveau)` : la table `progression` n'a pas cette colonne de ce nom.

## Architecture

- **Toutes les routes sont déclarées dans `index.php`** (appels `$f3->route`) ; aucun contrôleur ne s'auto-enregistre. Aucune route n'a de préfixe `/mini-grammaire`.
- `composer.json` n'a **pas** de section `autoload` : les classes `App\...` sont résolues par l'autoloader F3 (`AUTOLOAD` = `./`), donc `App\Controllers\X` doit être dans `App/Controllers/X.php` et le CWD être la racine du projet.
- Rendu d'une vue : `$f3->set('content', $tpl->render('pages/x.html')); echo $tpl->render('layout.html');`. `ui/layout.html` injecte `{{ @content | raw }}` et charge **toujours** `assets/js/script.js` + `assets/js/quiz.js` ; les CSS/JS propres à une page sont déclarés *dans* le template de la page.
- Syntaxe template F3 : `{{ @var }}`, `<repeat group="{{ @liste }}" value="{{ @item }}">`, `<check if="...">`. ⚠️ tout `{{ @... }}` écrit pour être *affiché* est interprété → 500 (cf. `/docs` ci-dessous). Un modificateur n'est accepté que si c'est une **fonction PHP existante** (`| esc`, `| strtolower`) : `| if(...)`, `| upper`, `| ord` n'existent pas, utiliser un ternaire `{{ @a == @b ? ' selected' : '' }}` ou un libellé calculé en PHP. ⚠️ un `<check>` écrit **sur une seule ligne** ne rend rien : le mettre sur ses propres lignes. Préférer les libellés (pluriel, majuscules) calculés dans le contrôleur à un `<check>` dans une boucle.
- Modèles : `\DB\SQL\Mapper` + nom de table en dur. Seul `User` impose la connexion (`new User($f3->get('DB'))`) ; `Astuces`, `Favori`, `Progression`, `MiniGrammaire` et `Quiz` prennent `?\DB\SQL $db = null` avec repli sur `\Base::instance()->get('DB')`. `Streak`/`ConsecutiveDays` n'héritent pas du Mapper (SQL brut + transactions) et n'existent pas comme modèles F3.
- ⚠️ `DB\SQL\Mapper` définit déjà `insert()`, `update()`, `erase()`, `find()`, `load()`, `count()` : **ne jamais nommer une méthode de modèle `update()`/`delete()`**, sinon PHP lève une erreur de signature au chargement de la classe (`php -l` ne la voit pas). Préfixe utilisé par `Quiz` : `createQuestion()`, `updateQuestion()`, `deleteQuestion()`.
- ⚠️ `Mapper::load()` appelle `reset()` avant de charger : il **écrase** l'instance (elle devient `dry()` si la recherche ne trouve rien, ou pointe l'autre utilisateur si elle trouve). `User::findByUsername()`/`findByMail()` sont donc **non mutantes** : elles passent par `find(..., ['limit' => 1])` et renvoient `reset($rows)` (raisin : dans `updateProfile`, un `load()` raté laissait `$this->email` à `null` et déclenchait à tort « Cette adresse courriel est déjà utilisée »). Toujours préférer `find()` à `load()` pour une simple lecture.
- Cache F3 sur disque : templates compilés dans `tmp/`, données dans `tmp/cache/`. `MiniGrammaire` y met en cache `mgc.all` / `mgc.parents` (TTL 600 s), `Quiz` `quiz.categories` / `quiz.menu` (TTL 300 s, vidés à chaque écriture) → **vider `tmp/cache/`** pour vérifier un effet fait en SQL direct.
- Session : passer par le hive F3 (`$f3->get/set('SESSION.*')`), pas `$_SESSION` directement. `BaseController::beforeroute` charge l'utilisateur, pose `userRole` (`invite` par défaut), `isAdmin`, `canDashboard` et `csrfToken`.
- **Message flash** : `BaseController::beforeroute` lit puis **vide** `SESSION.flash` (variable `flash`) ; `ui/layout.html` l'affiche une seule fois sur toutes les pages (classes `.flash`/`.flash-success`/`.flash-error` de `assets/style.css`). Un contrôleur ne doit **plus** consommer `SESSION.flash` lui-même, sinon le message n'apparaît pas. Les messages sont posés puis suivi d'un `reroute()`.
- `Page`, `QuizController`, `AstucesApiController` et `QuizApiController` héritent de `BaseController` (pour `canDashboard` dans la navbar et `requireRole()`). `Page::grammaire/grammaireDetail` testent toujours le rôle à la main via `in_array($f3->get('userRole'), BaseController::EDITOR_ROLES, true)`.
- **Tout le code, les commentaires, les textes UI et les messages de commit sont en français.**

## Responsive (toutes les pages)

- `assets/css/responsive.css` est la **seule couche responsive transverse**, déclarée dans `ui/layout.html` (donc sur toutes les pages du layout) : largeurs fluides, `overflow-x: hidden`, grilles auto-fit, conteneurs `.table-container` défilables, et une couche « ergonomie tactile » qui donne `min-height: 44px` aux liens/boutons cliquables sous `768px`. Les liens **inline dans un paragraphe** reçoivent un `padding` vertical (le padding vertical d'un élément inline n'agrandit pas la hauteur de ligne) : ne pas les passer en `inline-flex`, ça casserait le flux du texte.
- ⚠️ `overflow-x: hidden` sur `html`/`body` **masque** les débordements : ne pas s'en servir comme preuve qu'une page est correcte. Mesurer `document.documentElement.scrollWidth` vs la largeur de la fenêtre (neutraliser la propriété avant la mesure).
- `/docs` est une page **autonome** (son propre `<style>`, pas de layout, donc ni `responsive.css` ni le header) : toute modification de mise en page doit être faite dans son CSS inline, media queries comprises.
- Le header (`ui/partials/header.html` + `.nav-profile-actions` dans `assets/style.css`) garde les liens « Tableau de bord » et « Mon Profil » **sur la même ligne** (écart 25px). Sous `300px` l'écart passe à 10px plutôt que de les empiler.
- Vérification : audit Chrome headless sur `/tmp/opencode/audit_responsive.js` (largeurs, débordement, texte rogné, cibles tactiles). Attendu : **0 débordement** et **0 cible < 30px de haut sous 768px**.
- `ui/pages/auth_forgot.html` est **vide** (0 octet) et listé « ne pas toucher » : la route `GET /forgot-password` renvoie donc une page blanche. Le flux réel passe par le formulaire intégré de `/login` (`#forgot-password-form` → `POST /forgot-password-process`).

## Tableau de bord (`/dashboard`)

- Une seule URL, deux rendus selon le rôle : `pages/dashboard/admin.html` ou `pages/dashboard/enseignant.html` (`DashboardController::index`).
- Contenu pédagogique (CRUD complet, suppression définitive possible) : `admin` + `enseignant` → `/dashboard/astuces`, `/dashboard/codes`, `/dashboard/quiz` (questions de quiz).
- Comptes utilisateurs : `admin` seul → `/dashboard/utilisateurs` (`ADMIN_ROLES`). Jamais de suppression physique : `User::softDelete()` / `User::restore()` font alterner `users.deleted_at`, et un administrateur ne peut ni se désactiver ni changer son propre rôle.
- Journal des requêtes : `admin` seul → `/dashboard/logs` + `POST /dashboard/logs/purge` (voir « Journal des requêtes »).
- Toutes les actions POST passent par `csrfGuard($f3, $routeDeRepli)` puis `reroute()`.
- Les 7 vues sont dans `ui/pages/dashboard/`, le CSS dans `assets/css/dashboard.css` (déclaré dans chaque vue), la navigation repetitive dans `ui/partials/dashboard_contenu.html`.
- ⚠️ `mini_grammaire_codes.code` n'est **pas** unique (158 fiches, 133 codes distincts) : `MiniGrammaire::validateEntry()` ne doit pas contrôler l'unicité du code, sinon l'enregistrement d'une fiche `G1.1` existante est refusé.

## Quiz (`/quiz`)

- **Les questions vivent en base**, plus dans le JS. `assets/js/quiz.js` (chargé par le layout sur toutes les pages) appelle `GET /api/quiz/questions?categorie=…&niveau=…` → `QuizApiController` → `Quiz::questionsFor()`. Réponse : `{ success, categorie, niveau, quiz, message, questions: [ { question, level, options: [...], correct, explication } ] }` ; `correct` est l'**index** de la bonne option.
- Un quiz = couple `(categorie, niveau)`. `niveau = 'tous'` = test de niveau (mélange les 20 questions, CECRL inchangé) ; sinon `niveau` = niveau du quiz et `difficulte` = niveau de la question. Niveaux : `a1`…`c2`. `categorie` est le **slug** dérivé du libellé (réutiliser `Quiz::slugify()`), la bonne réponse est renvoyée au client (inchangé : le quiz n'est pas sécurisé).
- `GET /quiz` → `QuizController::index` : menu **généré depuis la base** (`Quiz::listQuizzes()`, cache `quiz.menu`), donc une nouvelle catégorie apparaît sans toucher au code. `GET /quiz/jouer/@categorie/@niveau` → `QuizController::jouer` : **connecté requis**, tokens reçus dans `array $args` (F3 passe le tableau du `@jeton` en 2ᵉ argument), `data-test="1"` uniquement pour `niveau/tous`. `GET /test-niveau` → `Page::testNiveau` redirige vers `/quiz/jouer/niveau/tous` (page réelle : `ui/pages/quiz/test_niveau.html`).
- Une question a **2 à 6 propositions** (nombre choisi à la création) ; `Quiz::validate()` (privée) retire les propositions vides mais **recalcule l'index de la bonne réponse** pour qu'il suive ce déplacement (sinon l'enseignant coche « A droite » ligne 4, les 2 lignes du milieu sont vides et c'est « B gauche » qui devient bonne réponse). Elle refuse aussi une bonne réponse vide ou hors bornes. `DashboardController::quizPayload()` / `indexCorrect()` convertit `POST.correct` (`A`…`F` **ou** index `0`…`5`) en index.
- Codes HTTP de l'API : `401` non connecté, `400` quiz non identifié (`categorie` vide ou `niveau` hors liste), `200` sinon — le client (`quiz.js`) n'utilise que `success` + `message`.
- `POST /quiz/save-level` enregistre la progression du test de niveau (inchangé). Le récapitulatif est affiché côté client ; CSS dans `assets/css/quiz.css`.
- Gestion : `ui/pages/dashboard/quiz.html` (une carte par question avec son formulaire d'édition en `<details>`) + `assets/js/quiz_admin.js` (bascule 2–6 propositions, valeur `correct` = index numérique) ; toutes les écritures sont transactionnelles et vident le cache.
- La liste du dashboard est **regroupée par libellé de catégorie** (`DashboardController::groupQuizByCategorie()` → `quiz_groupes`, bandeau `.quiz-groupe`) : `Quiz::listQuestions()` trie donc `categorie ASC, niveau ASC, id ASC`, sinon les questions d'un même quiz seraient mélangées. Renommer un libellé déplace le groupe et garde l'URL (c'est le slug `categorie` qui sert d'identifiant). Tous les libellés pluriels sont calculés en PHP (`Quiz::questionsLabel()`, `Quiz::questionsAfficheesLabel()`, `DashboardController::quizNombresPropositions()`).


## Journal des requêtes (`/dashboard/logs`)

- Une ligne par requête **PHP** (les assets statiques ne passent pas par PHP). L'écriture se fait dans un `register_shutdown_function()` posé par `RequestLog::demarrer()` (`index.php`) : c'est le seul moyen de couvrir les contrôleurs qui terminent par `exit()`/`reroute()` sans passer par `ONLOAD`. Le statut HTTP et la durée (`REQUEST_TIME_FLOAT`) sont donc mesurés au moment de l'écriture.
- `BaseController::beforeroute` appelle `RequestLog::setUtilisateur()` après le chargement de l'utilisateur ; le modèle se rabat sur la session au moment du shutdown, ce qui attribue correctement une ligne dont la session a été créée pendant la requête (connexion, inscription).
- ⚠️ `DB\SQL\Mapper::__construct` appelle `$db->schema($table)` et ** lève une exception si la table n'existe pas** : vérifier `RequestLog::tableExiste($db)` (statique, SQL direct) **avant** d'instancier `new RequestLog($db)`, sinon `/dashboard/logs` renvoie 500 au lieu d'afficher l'avertissement. Le shutdown est, lui, déjà encapsulé dans un `try/catch` : l'absence de table n journale rien et ne casse rien.
- Filtres de `DashboardController::logs()` : `q` (chemin/URI), `user_id`, `statut` (valeur unique = seuil, `>=`), `depuis`/`jusqua`, `page` (50 lignes/page, borné par `RequestLog::liste()`). Les valeurs invalides sont ignorées silencieusement, pas d'erreur SQL. `RequestLog::requetesLabel($n, $suffixe)` construit les libellés accordés (« 1 requête affichée »).
- Purge : `RequestLog::purger($jours)`, `0` = tout effacer. Rétention automatique `RETENTION_JOURS = 30` avec `PURGE_CHANCE = 50` (une requête sur 50).
- Aucun corps de requête n'est journalisé (volontairement : mots de passe). `referer` est tronqué à 255 caractères comme les autres champs texte.
- `request_logs` n'est jamais purgée par une autre action métier ; la table ne grossit que d'une ligne par requête.

## Sécurité — conventions à respecter

- Droits d'édition : passer **toujours** par `BaseController::EDITOR_ROLES` (`['admin','enseignant']`, liste blanche stricte : un rôle inconnu/erroné est refusé) ; `ADMIN_ROLES` (`['admin']`) pour les comptes utilisateurs.
- Toute écriture doit valider le CSRF : `csrfValidate($f3)`, plus soit `<input type="hidden" name="csrf_token" value="{{ @csrfToken }}">` (formulaire) soit `<script>const CSRF_TOKEN = '{{ @csrfToken }}';</script>` + en-tête `X-CSRF-Token` (AJAX). Jeton en session, comparé avec `hash_equals()`.
- Les champs du formulaire `/register` s'appellent `name` et `name2` (nom, prénom) — **pas** `nom`/`prenom` : `Auth::register` (Auth.php:88) fait `trim($f3->get('POST.name'))` sans cast, donc un champ absent ou mal nommé provoque un 500 (`trim(): Passing null`).

## Blocage des robots

Le site est privé : rien ne doit être indexé. Trois couches complémentaires, à maintenir ensemble.

- `robots.txt` (racine) : `User-agent: *` + `Disallow: /`. Simple demande polie, respectée par Googlebot, Bingbot, DuckDuckBot… **sans effet** sur un robot malveillant.
- `.htaccess` (racine) : filtrage **réel** sur Apache, donc **en production**. 4 blocs dans cet ordre : (1) signatures de robots/scanners → 403 ; (2) `App/`, `ui/`, `vendor/`, `migrations/`, `tmp/`, `phpmyadmin_secret_xyz/`, `composer.json`, `*.sql`, `.env*`, `*.bak|old|orig|swp|log|ini` → 403 ; (3) routage vers `index.php` ; (4) en-têtes (`X-Robots-Tag`, `X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy`). L'ordre compte : le filtrage doit précéder le `RewriteRule ^ - [L]` du routage, sinon il est court-circuité pour tout fichier existant.
- `.ddev/nginx/anti-robots.conf` : **équivalent nginx** pour DDEV, inclus par le `include /mnt/ddev_config/nginx/*.conf;` en fin de `nginx-site.conf`. Ne **jamais** modifier `.ddev/nginx_full/nginx-site.conf` : il porte `#ddev-generated` et DDEV le réécrit à chaque `ddev start` (même si on retire la ligne, la simple mention du texte dans un commentaire suffit à déclencher la régénération).

Pièges vérifiés le 2026-09-29 :

- **Ne pas mettre `curl` ni `wget` dans la liste des User-Agents bloqués.** Le healthcheck DDEV (`/healthcheck.sh` → `curl --fail -s 127.0.0.1/phpstatus`) envoie `User-Agent: curl/8.14.1` ; le bloquer rend le conteneur `unhealthy` (`phpstatus:FAILED`), fait échouer `ddev restart` et casse l'accès au site.
- **Ne pas bloquer un User-Agent vide** : mêmes outils de monitoring concernés.
- Sous nginx, un `location ~* ^/(App|ui)` est **inopérant** pour les `.php` : la regex `location ~ \.php$` (FastCGI) du bloc `server` est définie avant l'include et gagne. Il faut un préfixe `location ^~ /App` (le `^~` arrête la recherche par regex). Un `location ~* \.php$ { deny all; }` supplémentaire provoke « duplicate location ».
- Seuls `/assets/**` et `robots.txt` doivent rester lisibles en accès direct. `App/`, `ui/`, `vendor/` et `migrations/` doivent répondre **403** : sinon `/App/Models/User.php` est exécuté (FATAL error renvoyée en clair) et `/ui/pages/*.html` est servi tel quel.
- `assets/css/noscript.css` est référencé par `ui/layout.html` (balise `<noscript>`) et est **nécessaire** : s'il manque, toutes les pages renvoient un 404 d'asset.
